# Private Scheduler Run Lifecycle (Phase 24C2B)

| Layer | Authority | Status |
|---|---|---|
| 24C2A | Canonical run admission (`docs/PRIVATE_SCHEDULER_RUN_ADMISSION.md`) | closed |
| 24C2B | Lifecycle and claim-lease transition authority (this document) | implemented |
| 24D | Persistence: run-idempotency uniqueness, atomic `state_version` CAS, claim storage, queue / worker runtime | deferred |

Module: `backend/engine/private/scheduler_run_lifecycle.py` (pure, in the static-guard `PURE_MANIFEST`; standard library plus the closed 24C2A admission type and the 24A trigger-kind enum).

## Run admission -> lifecycle

`PrivateSchedulerRunLifecycle` (eight stored fields: `admission`, `state`, `state_version`, `claim_key`, `claimed_at`, `lease_expires_at`, `terminal_at`, `failure_code`) snapshots ONE admitted run. The admission is retained by identity through
every transition and the logical identity stays `admission.run_idempotency_sha256` (no second identity). States: `READY`, `CLAIMED`, `SUCCEEDED`, `FAILED` (no pending, running, completed, error, retrying, cancelled or skipped).

```text
READY      state_version == 1; no claim, lease, terminal time or failure code
CLAIMED    state_version >= 2; claim key, claimed_at, lease_expires_at; claimed_at < lease_expires_at; no terminal fields
SUCCEEDED  state_version >= 3; claim fields; terminal_at; claimed_at <= terminal_at < lease_expires_at; no failure code
FAILED     as SUCCEEDED plus a failure code (strict lowercase identifier; never exception text, stack traces, PII or provider bodies)
```

Stored instants are canonical UTC only (`tzinfo is timezone.utc`; non-UTC equivalents and subclasses are rejected, never converted). `claim_key` is opaque (1..128 printable trimmed characters, case preserved, generated by the caller / runtime, never here).

## state_version / expected_version CAS contract; no distributed atomicity

Pure Python validation cannot prove two workers did not read the same state concurrently. The domain therefore defines `state_version` plus the caller's `expected_version` (must equal the snapshot version, no hidden repair), the `claim_key`
and the half-open lease `[claimed_at, lease_expires_at)` (at exactly `lease_expires_at` the claim is expired). Every successful transition increments the version by exactly one; no caller chooses it. A valid transition means only:
*if storage applies it atomically against `expected_version`, it is domain-valid*. A valid CLAIM does not prove this worker won a distributed race. **Phase 24D must implement the atomic compare-and-swap**
(conceptually `UPDATE ... WHERE run_idempotency_sha256 = ? AND state_version = expected_version`, exactly one row) and uniqueness on the run idempotency.

## Transitions (each returns a `PrivateSchedulerRunTransition(kind, before, after)`)

- `INITIALIZE`: admission -> `READY` version 1 (`before is None`).
- `CLAIM` (`READY` only): `claimed_at` must not precede the run not-before instant: `trigger.scheduled_for` for a scheduled trigger and `trigger.cause_available_at` for an event-driven trigger (UTC instants, no tolerance, no clock); `claimed_at < lease_expires_at`.
- `RENEW_CLAIM` (`CLAIMED`, same claim key): only while the old lease is active (`claimed_at <= renewed_at < lease_expires_at`; at the expiry instant it is too late), new expiry strictly later; the original `claimed_at` is kept and `renewed_at` is not stored.
- `TAKE_OVER_EXPIRED_CLAIM` (`CLAIMED`): only at or after the old expiry (`claimed_at >= old lease_expires_at`; one microsecond early fails) with a different claim key. This is lease recovery, not a retry of a terminal run; the old claimant is invalid afterwards.
- `SUCCEED` / `FAIL` (`CLAIMED`): by the exact current claim key (case sensitive) and only while the lease is active (`claimed_at <= terminal_at < lease_expires_at`); a stale claimant cannot finish after a takeover.

`SUCCEEDED` and `FAILED` are final: every transition function rejects them (no reclaim, renew, reset or retry). **FAILED has no retry in v1**: no attempt count, `retry_after`, backoff or reset transition; any future retry policy must be explicit and
must not turn one logical run into several attempts silently.

## Transition records preserve before / after provenance

`PrivateSchedulerRunTransition` re-validates, on direct construction, the relation of `after` to `before` through the single relation check also used by the transition functions: admission identity by `is`, exactly one version step, the allowed
state change, claim-key, claimed_at and lease rules, and the not-before frontier. Transient inputs (`renewed_at`, `expected_version`) are checked by the transition functions only, since they are not stored. An equal-but-distinct admission clone is rejected.
